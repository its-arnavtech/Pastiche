# 0024 Lane core placement: priority plus pinned core sets, one mechanism

- Context: under the round-1 combined sustain the CPU render lane fell to 2.4 rendered audio-s/s and the NPU host to 14k inferences/s while the GPU held 94 %. A probe measured the GPU-lane process alone at ~5.4 logical CPUs (light and heavy Demucs alike), more than the 4 feeder cores budgeted, so 16 render workers + GPU process + NPU host oversubscribed the 20 usable CPUs. The brief asks for the GPU lane at above-normal priority with its feeder cores pinned and the CPU lane on the remaining cores. No second GPU-lane agent (opus-cc-2) produced affinity code (no branch, changelog or task), so there was nothing to merge; this decision extends decision 0012 rather than adding a parallel path.
- Decision:
  - `core_plan()` in the compute adapter derives disjoint lane sets from Windows CPU sets (gpt-sol's read-only `cpu_topology` adapter): gpu = first P-core (both threads, kernel launch) + `feeder_cores` E-cores; npu = the low-power island's first CPU; reserve = the next; cpu = everything else. On this machine: gpu 0-5, cpu 6-19 (14), npu 20, reserve 21.
  - One mechanism applies it: `bench stress` sets `REMIXER_CPU_AFFINITY` per lane process; `remixer.cli.main` pins itself from that variable before any work, and spawned workers inherit the mask. Above-normal priority stays where decision 0012 put it (`prioritize_current_process("gpu")`). At 100 % the CPU lane runs one render worker per pinned CPU. `--no-pin` restores OS scheduling for comparison.
  - Starvation is logged by the GPU lane itself: every metrics window it reads NVML utilization; GPU < 80 % while the prefetch queue was empty when the GPU asked for work appends a `gpu_starvation` event and a warning. Reports count events per step.
- Alternatives: affinity calls inside each lane's code (touches gpt-sol's renderer and NPU code, three implementations); priority alone (round 1 shows it is not enough).
- Consequences: lanes cannot steal each other's CPUs; a lane that needs more CPU shows it as its own cores saturating. Unpinned runs remain reproducible with `--no-pin`.

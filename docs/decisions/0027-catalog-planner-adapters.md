# 0027 Catalog-backed planner adapters: exact stem scan, separate recipe tables, lineage-wide deletion

- Context: T-023, T-024 and T-025 ask the core to provide the planner Protocols from decision 0018 (StemCatalog, NeighborQuery, RecipeStore, Lineage, deletion). The existing schema already had `recipes`/`recipe_stems` tables from T-002, with columns that predate the planner's content-addressed model and that nothing writes to. The CLAP HNSW index holds both stem-level and 5-second window vectors.
- Decision:
  - `remixer.adapters.planner_catalog` holds all of it. `load_stem_catalog(adapters)` builds a `StemMeta` per stem from `stems` + `analysis` + stem-level `embeddings` rows (the latest embedding version by default), reads the vectors back from the HNSW index (`HnswIndex.get`), and returns the planner's own `InMemoryCatalog`. `nearest` and `within` are an exact scan of the stem matrix: exact answers satisfy the "exact or superset" rule with no tuning, and a tenant's few thousand stems take about 1 ms per query. Stems without analysis, a parseable key or an embedding are skipped.
  - `analysis_row()` maps a `remixer.cpu.analyze` result into the `analysis` table (tempo, key, LUFS, beats, energy curve, meter/downbeat/duration in `meta`).
  - Recipes live in new tables `recipe_versions` (canonical bytes keyed by recipe_id, root, version, supersedes, batch), `recipe_lineage` and `recipe_refs` (kind song|stem|window -> recipe ids, indexed). The legacy `recipes`/`recipe_stems` tables are left untouched, so no migration is needed for existing catalogs.
  - `delete_track(catalog, song_id)` removes every lineage any of whose versions used the song (later versions are derived from it even after a ban removed the song), their lineage/ref rows, renders and exposure rows, the song's stems, windows, analysis and embedding rows, and its playback and rating rows. `delete_tenant(catalog)` empties the tenant's catalog. Both return the blob keys to delete; vector-index and Parquet event files are per-tenant directories that the caller removes with the tenant.
  - Tenant scope is the catalog itself (one per tenant data directory in the local profile).
- Alternatives: HNSW search with stem filtering (approximate, and stems compete with about 50x as many window vectors); reusing the legacy recipe tables (wrong shape, would need a migration); deleting only the versions that contain the song (leaves later versions whose history no longer resolves).
- Consequences: contract tests cover the catalog against the in-memory reference, a planner run and both kinds of ban on real adapters, tenant isolation and deletion (`tests/contracts/test_planner_catalog.py`, `catalog` backend in `RECIPE_BACKENDS`). Beyond about 100k stems per tenant, switch `nearest` to a stem-only HNSW index; `within` should stay exact.

# Unit economics (POC 2, paper only)

Cost per processed hour of audio and per active user per month, for the commercial profile (`docs/commercial.md`).
**Measured** means measured on the POC 1 laptop and cited. **ASSUMPTION** means nobody measured it here: a price, a
compression ratio or a user behaviour. Every number below is regenerated by `uv run python tools/unit_economics.py`;
change an assumption there and rerun. Nothing here was quoted from a vendor, and no money was spent or committed.

| Input | Value | Source |
|---|---|---|

| Demucs light, all lanes on, 15 min, final configuration | 58.40 audio-s/s | `docs/PEAK_REPORT.md`, round 3 |

| CPU render (stretch, shift, mix), 8 workers, GPU idle | 12.64 rendered audio-s/s | `docs/PEAK_REPORT.md`, round 2 CPU ramp |
| CPU render, 8 workers, GPU busy (shared cooling) | 2.89 rendered audio-s/s | `docs/PEAK_REPORT.md`, round 3 sustain |
| Analysis, 16 workers | 154.71 files/min; a file is 3.59 min on average | `docs/reports/cpu-lane.md` |
| Taste scorer on the NPU | 47,447 inferences/s | `docs/PEAK_REPORT.md`, round 4 sustain |
| Stem storage | 4 x 42,594,252 bytes for a 241.5 s track = 2.54 GB per audio hour (WAV, 44.1 kHz, stereo, 16 bit) | `data/stems/` |
| Vector storage | 195 MB for 88,816 vectors = 2.2 KB each, plus 1 KB per window as fp16 | `data/vectors/`, `data/embeddings/` |
| Analysis JSON | 196 KB per 4.02-minute track (5 files) = 2.9 MB per audio hour | `data/analysis/` |

The laptop's numbers are thermally limited (GPU `sw_thermal` in 88-97 % of samples). A datacenter GPU would not be, so the
"sustained" column is a conservative stand-in, not a forecast.

## 2. GPU-seconds per audio hour (measured, then priced)

| Stage | Working | GPU-seconds per audio hour |

| **Total** | | **83.0** (75.4 best) = 0.0230 GPU-hours |

Priced (ASSUMPTION: a cloud GPU separates as fast as this laptop's thermally limited GPU; the range is 0.5x to 2x):

| GPU price (ASSUMPTION) | Per audio hour | Per 3.5-minute track |
|---|---:|---:|
| $0.25 per GPU-hour (spot, small GPU) | $0.0058 | $0.00034 |
| $0.40 (base) | $0.0092 | $0.00054 |
| $1.00 (on-demand) | $0.0230 | $0.00134 |

Heavy Demucs (`htdemucs_ft`, 2 shifts) would cost 491 s per audio hour, 6x the light model. The stable preset does not use it.

Separation is a one-off per distinct audio file (content-addressed, cached forever). A shared catalog of 10,000 tracks of 3.5
minutes (583 audio hours, ASSUMPTION) costs **13.4 GPU-hours once: $3.36 to $13.45** depending on the GPU price above.

## 3. CPU cost per audio hour (measured, then priced)

| Stage | Core-hours per audio hour | At $0.04 per core-hour (ASSUMPTION, spot vCPU) |
|---|---:|---:|
| Analysis (4 stems) | 0.115 | $0.0046 |
| Render, isolated | 0.633 (3600 / 12.64 x 8 workers / 3600) | $0.025 |
| Render, hot laptop with the GPU busy | 2.77 (3600 / 2.89 x 8 / 3600) | $0.111 |

One 32-second recipe renders in about 20 core-seconds ($0.00023), or 89 core-seconds on the hot laptop. A render is only needed
when a user plays a recipe, and section caching means a ban re-renders only the sections it touched (`docs/ACCEPTANCE.md`,
demo: 5 of 16 sections).

## 5. Per active user per month

Behaviour (ASSUMPTION): 20 listening hours, 15 listens per hour, about 6 events per listen (the demo's scripted listens
averaged 3.6), 100 recipes played.

| Item | Working | Cost |
|---|---|---:|
| Events | 1,800 events x about 60 bytes compressed = 0.11 MB of Parquet | under $0.00001 |
| Planning | pure CPU, seconds per batch (`planner/scale.py`) | negligible |
| Recipes rendered on a server | 100 x 20 core-seconds x $0.04 per core-hour | $0.0225 |
| Recipes rendered in the browser | 0 server CPU; each recipe fetches about 2 MB of stems at 128 kbps (ASSUMPTION) | $0 on a no-egress store, $0.018 at $0.09 per GB egress |
| Share of the catalog's storage | see section 4, divided by monthly active users | $0.002 to $0.034 at 1,000 MAU |
| Hosted LLM insights | about one insight per day, a handful of short calls per night | not measured; estimate under $0.05 on a small hosted model (ASSUMPTION) |

**Summary (all ASSUMPTION-priced):** with a shared, pre-separated catalog and client-side rendering, marginal cost per active
user is a few cents per month; at 1,000 MAU the fixed cost of storing the catalog is of the same order. Cost per user rises
if users bring their own audio to separate server-side (path b with uploads is not allowed, see `docs/legal-paths.md`), if
renders move server-side at hot-laptop efficiency, or if stems stay lossless.

## 6. What would change these numbers

- Measure a cloud GPU's separation rate; the 0.5x to 2x spread moves section 2 by the same factor.
- Measure FLAC and Opus sizes on real stems and check that remixing quality survives lossy storage.
- Replace the price assumptions with quotes. All prices above are placeholders; they were written from memory of public price
  pages and have not been checked.
- Record compute seconds, GPU seconds, storage and egress per tenant as events from day one (POC 2 spec section 3). The hooks
  do not exist yet.
- Taste training on real ratings and the larger local LLM (`docs/KNOWN_LIMITATIONS.md`) are not in this worksheet.
